# Collatz PR Review Gate

> **Stage 1 routing:** steps 2–9 below that perform a code-review action are `effect_label = "code_review"` and MUST route through `formal-math-effect-dispatch`. The reviewer subagent runs on `openai/gpt-6.1-terra` (per step 3) — explicitly *not* the orchestrator's model — and gets the restricted `tools_allow` declared by the dispatcher. Pushing remediation steps that modify source code remain `op_LLM` with `trust_boundary_change=true` and may NOT be performed by the reviewer subagent.

Use for every implementation pull request in `johrenberger/collatz-research` after a pushed head exists.

1. Before changing PR-gate policy or documentation, inspect the checkout and branch. If an active feature PR exists, use a separate clean worktree or branch so the policy and feature diffs remain isolated. Completion: the diffs are separate.
2. Record the PR number, full head SHA, story, acceptance criteria, trust-boundary changes, validation evidence, and known limitations in the PR template. Completion: the reviewed SHA is explicit.
3. Before review handoff, verify that `openai/gpt-6.1-terra` is registered and route-compatible for isolated subagent runs. Completion: the reviewer can start without registration or authentication-route errors.
4. After every PR create or update, create an internal review handoff keyed by `repository/pr-number/head-sha/review-round`. Start an isolated `openai/gpt-6.1-terra` reviewer with read and PR-review access only; it must not edit source or merge. **One reviewer per head SHA.** Never start a second reviewer for a SHA that is already under review, and never start reviewers in parallel for the same PR: each additional reviewer re-reads the repository and the diff from scratch, and that fan-out is the dominant token cost of this gate. When the head moves and another round is needed, resume the existing reviewer session with a follow-up message naming the new SHA, so its transcript, prior findings, and confirmed-sound checklist carry forward. Resumption is keyed by the reviewer session's continuation handle, which the reviewer records in its durable receipt; the later round still creates its own round-inclusive handoff, so the rounds stay distinct handoffs while designating one reviewer session. Start a fresh reviewer only when the handle cannot be resumed, or when a P0 calls for a genuinely independent second opinion — started serially, only after the first review of that SHA has completed and been classified, so two reviewers never hold the same SHA at once. Completion: the PR is `AWAITING_CODEX_REVIEW` with an auditable handoff, and the round's reviewer is the previous round's session unless a reason is recorded.
5. Have the reviewer inspect the exact SHA and post through the maintainer's connected GitHub identity, naming its model and full SHA and stating `Generated by independent OpenClaw Codex review`. Completion: the review is attached to the current head.
6. Fetch review submissions and inline threads; accept only reviews of the current full head SHA as merge-gate evidence. For P0, stop and reassess structurally. For P1, state a falsifiable remediation hypothesis, make one bounded change, and validate it. For P2, resolve it or obtain maintainer-approved deferral with a linked follow-up. Completion: every finding has an evidence-backed disposition.
7. Push remediations, update validation evidence, and create a new handoff; a push invalidates earlier approval. Completion: the new SHA starts the next review round.
8. Allow at most three remediation-review rounds per PR — the cap set by `docs/codex-pr-review-gate.md`, which this skill defers to as the repository protocol. Escalate on the third unresolved round. Each round after the first resumes the same reviewer session (step 4) and presents it the new head SHA together with its own prior findings; do not open a fresh full-context reviewer for the round. The audit measured that fresh-review fan-out — 20 reviewer sessions under one parent, 1,141,499 tokens — as the dominant cost of this gate, because a fresh reviewer re-reads the repository and the diff from scratch while a resumed one carries its transcript, prior findings, and confirmed-sound checklist forward. It did not isolate the round count itself as a variable, so do not treat that as measured. On an unresolved third round, a P0, or an architecture or mathematical decision, stop editing and escalate with reviewed SHAs, review URLs, findings, hypotheses, validation output, and the last-green commit. Completion: no speculative loop continues.
9. Request human merge authorization only when Codex approves the current head, required CI is green for that SHA, and no P0/P1 remains. Codex review never grants merge authority. Completion: PR state is `HUMAN_MERGE_READY`.
10. For a hotfix stacked on a merged PR, branch from the merged commit SHA rather than a prior ancestor. Before creating the PR, verify the staged diff with `git diff <base-sha>..HEAD`. Inspect `.github/workflows/*.yml` before claiming which files CI exercises. Completion: the PR diff matches the intended patch and CI claims are sourced from workflow YAML.

11. Close a multi-PR arc with ONE closing verification against the final tree, not with per-PR re-reviews. When several PRs of one arc merged carrying an unresolved verdict (the maintainer merged before the review landed), close the arc with: (a) an evidence-backed **disposition comment** on each affected PR naming where its finding landed, and (b) ONE closing review that checks the **union of every finding raised across the arc** against the final SHA and marks each one RESOLVED — a per-PR diff cannot show that a finding from the arc's first PR is still fixed in the tree produced by its last. Count the arc's files with `git diff --name-only <first-merged>...<final-head>` instead of summing per-PR counts, because files touched by more than one PR get counted twice. When a receipt declines to claim a local validation because it was still running, close that gap with the **gate's own CI step conclusion** for the reviewed SHA (`gh api repos/OWNER/REPO/actions/runs/RUN_ID/jobs --jq '.jobs[].steps[] | {name, conclusion}'`), not with a local re-run of the same script: the hosted job runs on the reviewed tree and a local re-run can outlast the job it is meant to predict. Completion: one APPROVE covers the arc, every historical finding has a disposition, and no validation gap is left open.

Consult `docs/codex-pr-review-gate.md` for the repository protocol.
